# 消息存档、引用元数据与历史检索

聊天原文与当前处理状态属于程序维护的本地资料。Codex 的近期输入和自动 compact
不是完整聊天记录的真值。长期存档、近期上下文和已确认人物记忆分别维护。

## 1. 存什么，保留多久

每个已接入对话保存收到的文字原文、发送者标识、平台提供的名字与时间、消息 ID、
@/提及、引用树、附件类型、图片元信息、QQ 语音转写及转写状态。人类之间的闲聊、
Jev 判为静默的消息和命令也入档。机器人发出的每个气泡保存原文、生成来源与 QQ 投递状态。
请求记录关联所有来源消息和版本；状态更新覆盖索引中的最新状态，首版不保存每一次状态变更的流水。

SQLite 存档独立于有时间/条数上限的短期 JSON 状态。短期清理、会话重置和 Codex compact
不会删除存档。各对话首次启动时导入当时尚存的记录；此后先保存 JSON，再提交存档，最后确认网关事件。
存档失败会明确使处理失败，不会一边确认收妥一边悄悄漏档。数据库、备份与聊天内容均不进入 Git。

覆盖范围是 **ClawMingle 实际收到的消息**，不是 QQ 账号的全部历史：

- 启用前已经清理、停机期间平台未补发、未获订阅权限的消息，不能声称已保存或能补拉。
- 平台引用若只有正文而缺少索引/时间，并且找不到本地原消息，时间和处理状态明确为未知。
- 原始音频未下载保存；语音存 QQ 转写。图片保留消息元信息，像素仍受独立媒体缓存期限限制。
  原始平台事件、卡片原始字段、文件/视频内容也不是本版完整存档范围；引用树有深度/大小限制并标注截断。
- 存档不自动到期或因额度删除旧记录。当前群聊数据根和私聊数据根各使用一个最大 128 MiB
  主数据库；短读快照、检查点和写前侧文件额度检查限制增长。事务中侧文件可临时增长。
  达到容量时明确报错，需维护容量或安排经确认的迁移，不能把有限磁盘称作无限保留。
- 数据库目录 0700、文件 0600，拒绝符号链接/硬链接；只读查询固定绑定当前对话。
  数据库不挂载到模型工作区，模型不能传入群 ID、文件路径或 SQL 来扩大范围。

## 2. 标识、时间和状态

“不单独回复”仅决定是否触发任务，不会排除后续上下文。Codex 的文字、语音转写和图片候选
使用同一个配置窗口，遵守会话重置边界并排除命令消息，不额外按短期任务关联时限过滤图片。
当前请求图片优先，其次为明确引用图片，再次为窗口内近期图片（包括静默消息和引用树中的图片）。
沿用每轮最多三张、每张 2 MiB 的视觉预算；重复图片共用输入，超限和读取失败明确标记，
不会拿另一张图替代。每个视觉绑定保留原消息序号、发送者、时间、来源类别与引用路径；
文字预算裁剪后仍保留这些归属信息。上下文图不成为新任务，也不被重复当作当前表情观察入库。

| 字段 | 含义 |
| --- | --- |
| `message_ref` | 本对话稳定标识：入站 `M<seq>`；机器人气泡 `B<request>.<从0开始的气泡序号>` |
| `message_id` | 已收到的 QQ 平台消息 ID；未知时为 null |
| `lookup_key` | 引用携带的原消息索引，可交给查询工具；与被动发送锚点不是同一字段 |
| `sender.kind / speaker / display_name` | 人类/机器人、稳定匿名化成员标识、平台提供的名字；名字可能为空 |
| `timestamp` | 毫秒时间戳、UTC、北京时间与时间来源；未知不猜测 |
| `processing.decision` | 待判断、判断中、完成、程序绕过或失败；Jev 任务尝试数、最后决定与其是否为当前结果 |
| `processing.request` | 所属请求、来源版本、当前版本、生成和投递进度、失败码、气泡状态计数 |
| `generator` | 机器人气泡来自模型回答、命令回复、失败提示，或旧记录的未知来源 |

发送者仍使用稳定匿名化标识，避免把平台成员 OpenID 当作自然语言姓名。
`timestamp.source` 分为 `qq_message`、`qq_send_ack`、`received_at`、
`send_acknowledged_at`、`unknown`。后两类本机时间不等于被确认的原始发送时间。
旧记录可能有数值时间但来源未知；缺失名字、ID、时间、状态均不虚构。

`decision.status` 为 `pending/running/completed/bypassed/failed`；机器人输出为
`not_applicable_bot_output`。`jev_attempts` 计 Jev 判断任务尝试，不计内部 HTTP 重试，
也不证明远端收到了请求。旧记录缺少该计数时为 null；已有 Jev 决定则能确认曾判断。
重试中可能保留上一轮决定，必须结合 `last_decision_is_current` 读取。

处理进度明确区分：

1. `pipeline_scheduled_revision`：进入回复流程，可能尚在读记忆、取图片，不能证明 Codex 已开始。
2. `codex_started_revision`：App Server 返回 `turn/start` 确认后记录，事件绑定请求与版本。
3. `successful_generation_revision`：完整回复准备成功，尚不证明发给 QQ。
4. `complete_delivery_revision`：该版本所有应发气泡已获得确认。

`source_revision`、`source_codex_started`、`source_reply_complete` 用于判断这条来源消息
是否已经覆盖，避免把旧版本的完成误说成新追加要求已回答。历史来源版本缺失时返回未知。
`Sent` 表示 QQ 确认发送，不是人类已读；部分成功、失败和未知投递分别保留。
失败提示即便发出，也不推进模型成功回复的游标。
没有成为请求的静默消息仍可能被模型看作其他请求的上下文，不能断言“Codex 从未见过”。

## 3. Jev 实际收到的格式

TypeSafe 请求仍是 `model + state + questions`；程序组装，不接受聊天原文替换规则。
`state` 主要字段：

- `policy`：参与模式、判断规则、引用/转写/元数据说明。
- `human_participants`：匿名化成员标识与可用名字；被提及但未发言的成员也可列入，名字未知时为空。
- `context_snapshot_at`：本次上下文快照时间。
- `current_message`：当前待判断消息的 `seq/metadata/speaker/timestamp_ms/content/at_bot/mentions/voice_inputs/quotes`。
- `recent_messages`：配置范围内最近入站上下文，包含未请求回复的人类闲聊；每条同样附元数据。
- `active_requests`：候选请求 ID、版本、所有者、状态、近期来源摘录；不是全部历史请求。
- `recent_bot_replies`：近期已发送回答的有界摘录。

引用 `quotes[]` 包括 `speaker/timestamp_ms/message_type/source/content/voice_inputs/attachment_kinds/
image_count/parts/content_available/grants_permissions/metadata`。
`metadata` 在判断时关联原消息的最新状态，包含上表的身份、时间和处理字段。
引用机器人也继续交给 Jev 判断，不自动强制回复。Jev 不持有历史查询工具；程序为其补全可精确匹配的旧引用。

`questions` 包含八项独立 typed choice，在同一次 API 调用完成：`reply_boundary`（明确不回复）、
`exchange`（对话对象）、`you_referent`（“你”的指代）、`participation`（是否参与）、
`relation`（固定四种任务操作）、`task_target`（另选任务）、`audience`、`style`。
直接对机器人说或“你”指机器人时进入回应；明确不回复优先。取消已识别任务不产生回复，
因此“停止，不用回复”仍可取消；所有权和版本检查照常执行。专注的人对人交流只阻止新插话，
不覆盖明确的机器人指代或已有任务操作。响应保留各分支原始选择、置信度和概率；
不存在一个能代表最终决定的 `relation.confidence`，元数据以 `branch_confidence` 分别报告。
表情输入还有独立的图片判别项。
Jev state 限 24,000 字节，超预算先裁去较早上下文等有界内容，不等于缺失内容已从存档删除。
`recent_messages_omitted_for_budget` 和 `recent_bot_replies_omitted_for_budget` 记录本次裁剪数量；
后台配置的条数是最多携带条数。近期入站消息保留身份、时间和处理状态，但省略详细版本计数和逐泡投递账目，
避免账目挤占聊天正文；Codex 历史查询工具仍可取得完整记录。

## 4. Codex 实际收到的格式

系统说明后附结构化 JSON：

- `context_snapshot_at`
- `current_request`：`id/revision/owner/audience/style/messages`；只有这里的来源定义当前要回答的请求。
- `group_context`：近期聊天（私聊也沿用这个字段名），包括未要求回复的消息。
- `already_delivered_bot_messages`：已获投递确认的模型回答，附时间、图片标记与元数据。
- `recent_sent_images`、`native_image_generation_enabled`：本轮可用的图片引用与能力开关。

来源和上下文消息包含 `seq/metadata/speaker/text/at_bot/mentions/native_reference_available/
quotes/attachment_kinds/image_count/voice_inputs`。引用使用与 Jev 相同的公共投影；
不传附件下载 URL、宿主机文件路径或成员 OpenID。图片像素另以模型 image 输入传入，
可用性通过精确的来源/引用路径绑定说明，不能仅凭 `image_count` 声称看过图。
另有按需注入的已确认群记忆、人格与启用 Skills；它们不替代原始聊天存档。
结构化消息输入限 128 KiB，历史工具返回也有独立上限。当前任务来源只在 `current_request`
提供完整正文，不再重复放入 `group_context`。近期窗口保留正文、身份、时间、引用、
生成/投递关键状态；详细版本计数和诊断由历史查询工具提供，避免账目挤占正文。

## 5. Codex 的两个只读工具

`clawmingle.message_lookup`：

```json
{"message_id":"M42"}
```

也接受本对话平台 ID、`B7.0` 或引用的 `lookup_key`。返回原文、引用、转写、身份、时间、
当前决定与请求进度。大段文字每次最多 12,000 字符，返回 `next_text_offset`；
继续带 `text_offset` 读取尾段，不将被截断的摘要称作全文。未知或歧义 ID 不猜测匹配。

`clawmingle.messages_list`：

```json
{"after":0,"limit":20,"since_ms":1792540800000,"until_ms":1792627199999,"contains":"烤鱼"}
```

时间为毫秒、含上下界；关键词按字面大小写敏感匹配正文、转写和有界引用文字。
每页 1–50 条，正文是 200 字符摘录；按 `message_ref` 可继续取原文。
有下一页时返回 `next_cursor/has_more`，下一次保持筛选条件并传入游标。
游标表示首次入档顺序，不等于发送时间，也不等于 `M` 序号；时间过滤使用消息时间。
每次工具调用读取一致短快照，跨页若发生状态变化，后页反映新的已持久化状态。

两工具均返回查询时间、覆盖范围、截断说明和内容不可信标记。单次返回最多 128 KiB；
过大时明确失败并要求缩小页面，不静默漏条。一轮最多 48 次历史读取，与普通工具预算独立。
查历史不会启动回复、修改模式、确认记忆或授予命令权限。工具在管理页和 `/tool` 中分别启停。
无需新增 `/history` 用户命令；用户自然说“看看上周我没得到答复的那条”时，Codex 可自行检索。

首次引用找不到原始索引/时间时，模型应说明缺项；不能从内容、消息 ID 形状或用户情绪倒推出时间。
当用户引用久未处理的消息表达不满，应先查原文、两个时间与处理状态，再解释或补答，
避免把不确定的处理过程说成事实。

## Codex 原生线程与任务连续性

独立请求使用独立的原生线程；同一请求的追加、修订、继续仍恢复该请求的线程，保留工具过程。
任务穿插时不借用另一任务的线程。每个新任务仍获得同一配置消息窗口、图片、Identity、Soul
与本会话记忆，聊天上下文不会因为换原生线程丢失。绑定随请求持久化；旧记录没有绑定时
从现有应用上下文开始，工具能力变化和会话重置不复用旧权限线程。
这样避免每句闲聊都把完整窗口追加进同一条不断膨胀的历史；不禁用原生压缩，也不增加长任务上限。
同一任务续轮的 `context_delivery.mode=delta` 只补充新增或变化的群聊与已投递回复，
当前任务的全部要求、相关正式记忆和图片绑定仍刷新。未改变的应用规则、Identity、Soul
和群档案可复用同一原生任务已有的版本；规则、人格或群档案发生变化时重发完整规则和消息窗口。
新任务提供按下述规则选取的配置窗口，不跨任务借用人格／上下文收据。

输入指纹在完整 prompt（包括记忆、图片归属等附加内容）组装后计算。`turn/start` ACK
只保存候选，既不证明模型已读取，也不推进生成／投递成功状态。下次续接先以
`thread/read(includeTurns=false)` 获取当前原生记录位置，再只读隔离运行目录内该线程的
实际 `response_item` 用户输入。候选输入和完整规则／消息基底均有精确匹配才启用增量。
不依赖历史面板的用户事件；展示历史可能保留已被压缩的原文。遇到原始压缩、回滚记录、
缺失／异常／不支持的历史、线程或策略变化均回到完整窗口。读取限制为 64 MiB 文件、
8 MiB 单行；超限只放弃优化，不删除历史或拒绝用户任务。此检查不产生模型调用。

执行中追加（steer）提交后清除旧候选；迟到的旧版本 ACK 不得恢复它。模型没有读到的
输入不会仅凭 ACK 被省略，已持久化的中断输入则可在下次验证后复用。候选校验状态
不写入持久数据，重启后重新核实。原生之后仍可能自动压缩；增量只是传输优化，不能
保证所有旧原文永远驻留模型上下文，精确内容通过历史查询工具取得。

热窗口只保留一份带时区的时间及其来源、稳定消息／成员标识、正文、引用、必要的生成与
投递状态。平台长 ID、备用时间格式、路由诊断、重复任务显示编号由历史工具按需提供。
省略的空字段表示未知或不适用，不代表完成或成功；显式 false 状态保留。
完整存档与查询结果不变；图片像素继续独立提供，不能用文字摘要替代。
不主动删除历史、不引入额外的模型摘要调用或任务时限。

## 上下文分层与参考实现

本项目把四类内容分开：完整聊天存档；有界近期窗口（包括静默消息和图片）；当前任务的
原生执行历史；按范围检索的正式记忆。闲聊新请求不会继承其他任务的全部工具记录，
同一任务的追加则保留原生执行历史，避免重复执行已经做过的外部操作。

参考 [OpenClaw 的消息与历史管理](https://docs.openclaw.ai/concepts/messages) 对静默消息、当前输入
和历史的区分，以及 [OpenCode 的摘要与近期回合保留](https://github.com/anomalyco/opencode/blob/70c69f06f9d7ae3103d923898d926d88f3c97f4d/packages/core/src/session/compaction.ts)
和 [工具输出外置](https://github.com/anomalyco/opencode/blob/70c69f06f9d7ae3103d923898d926d88f3c97f4d/packages/core/src/tool-output.ts)
设计。本轮采用减少重复注入、精简元数据、按需检索的方式；未照搬其阈值，也未新增摘要模型。
Codex 原生工具历史的压缩仍由 Codex 管理，宿主缩小输入不等于已经压缩原生历史。
接口依据：[OpenAI App Server 的线程启动和恢复](https://learn.chatgpt.com/docs/app-server)。

2026-10-25 的离线样本中，单次成功闲聊曾消耗 83,946 个输入 token；同一任务中断后
重复完整注入是已确认的膨胀来源。仅元数据精简的三份对比为 47,234→29,881、
47,071→29,726、47,680→29,644 UTF-8 字节；正文及每份三个图片输入项保持一致。
这是输入字节数对比，不是 token／延迟／限流改善的线上验证。


## 热聊时的输入选择与追加

在原有近期窗口内，其他请求已完整生成、确认送达且结束的来源文字不再自动重发。
例如 M1 已回复，M2/M3 静默，M4 新提问：M4 是当前请求，M2/M3 继续作为背景；
M1 原文保留在存档，可通过 message_lookup 查询。不会先过滤再向更早历史补足条数，
也不会移动全局 context_start_seq，因此交错的静默消息不会被“已回复游标”误删。

当前任务的来源始终保留；失败、部分/未知投递、等待澄清和缺少可靠版本记录的消息
不会被当作已回答。当前消息的引用仍包含原文。由于历史工具尚不能重新装载图片像素，
近期含图消息（包括引用图）继续保留，遵守原视觉预算。关闭 message_lookup 时恢复完整
文字窗口。最近机器人回复仍按已有配置提供，用于理解“为什么”等短追问。

mode-2/3 中真实 @ 若存在未结束请求，也进入 Jev 的任务关联判断；@ 不等于每次新建任务。
Jev 分别判断参与、关系和目标，候选任务提供首条和最近两条来源，避免只看到最后一张
表情就丢失任务主题。真实 @ 保证回复机会，明确要求不回复除外；Jev 不可用时独立建请求，
不猜测合并目标。失效、未知投递或无修改权限的关联目标不被强行修改。

执行中的追加使用既有 quiet_ms/max_wait_ms 收集窗口，默认静默 1.2 秒、最长 4 秒后
提交当前已判定的补充；持续有消息不会无限延长首次等待。每次只发送新来源、其身份/
引用/语音、最新版本与完整来源编号，以及新增周边消息。它明确是原生活动任务的补充，
不会重复注入 Soul、Identity、整段旧聊天或所有旧要求。只有原生 ACK 成功才推进基线；
失败或结果未知仍取消旧轮并以完整当前请求恢复。取消和权限变更不等待收集窗口；
新图片在收集合并后走完整输入重绑，避免复用错误像素。


## 高频群聊的执行边界与输入预算

Jev 每条消息到达后尽快判断，不再先等整群安静；八个逻辑问题仍独立。
是否参与、是否关联已有请求与何时调用 Codex 分开处理。已有请求记录继续保存
发起人、贡献者、来源消息和 revision；不同人的同时发言不会仅因相邻而合并。

每个排队请求按相关 revision 独立收集，默认安静 1.2 秒／最长 4 秒。
窗口到期时冻结需要完成判断的消息前缀；之后无关的新消息不延长该前缀。
前缀内的 Jev 判断需结束（失败也属于结束），关联修订仍检查安静窗口，
但不重置最早的最长收集期限。原生 steer 使用相同的有限前缀，明确取消仍即时处理。
每个待发气泡也有自己的前缀；后续气泡、失败后的恢复重新取前缀。
已知的新 revision、取消和上传后校验继续阻止旧版本发送。

`input_budget` 对固定指令、动态工具声明、当前请求及记忆／附件说明做文本估算后，
优先移除可通过历史工具恢复的较旧背景整条记录和已发送回复。保留当前请求全文、
最近四条背景、最近两条已发送回复、带图片／引用／语音的来源；不截断 Identity、Soul
或群档案。预算是软目标，必须保留的内容超过目标时继续保留。图像 token、原生工具
声明、原生历史和服务端指令不包含在这项文本估算里，不能作为账单 token 使用。
首次输入目标 12,000；已由 task_update 确认为长任务时，后续输入目标为 30,000。
预算不依赖 Jev 的回复风格标签，因此 mode-1 的普通 @ 闲聊也能使用轻量目标。
必需内容可以超过目标，最终使用量以原生事件为准。
策略指纹或原生历史无法验证时重发完整基线；精简后的候选不冒充已成功传入的内容。

每次执行向原生 Codex 传入 `model_auto_compact_token_limit=60000` 与
`tool_output_token_limit=4000`（可通过 `input_budget` 配置），使用原生压缩与输出预算，
不伪造模型窗口大小。原生压缩也可能产生模型请求，不是无限免费保留历史。
大于 16 KiB 的应用动态工具 JSON 返回，在当前执行具有工作区读取能力时，
保存完整副本到本对话工作区，只回传状态、操作标识、简短预览和文件路径。
模型按需读取字段或片段；工具已经执行，不应为获得全文再次执行修改操作。
无读取能力或保存失败时仍返回原结果，不把成功操作改成失败。
单份副本最多 8 MiB，工作区此类副本最多 128 份／64 MiB；不自动删除已有副本。
原生截图继续作为图像输入，不作为 base64 文本归档。

日志分别记录 prompt／工具声明／输出 schema 字节数、图像数量、文本估算，以及原生
根线程的累计 input/cached/output 和最近一轮 input。累计快照不能逐行相加；
根线程数字不代表父子 agent 合计。上线前的字节缩减不等于已测得线上 token 收益。

## 429 与共享模型入口

### 短回复合批与积压重审

`batching` 默认开启。同一会话中已完成收集、尚未执行过的独立请求，可以共享一次
轻量 Codex 执行；每条请求仍保留原 ID、发起人、来源、修订、引用、输出队列和发送状态。
同一任务的追加/修改继续使用原有语义关联，合批不会改变请求归属，也不会跨群/私聊。

模型入口允许尝试时，Jev 对待处理请求分别问两个独立的 Noul 问题：能否直接短答、
可选接话是否已经过时。问题一起发送，代码组合结果，不让所有请求竞争一个选项列表。
每次新的429会使先前重审失效；可选接话遇到新聊天或新交付时，旧结果不能再用于合批或撤回。
同一请求修订、权限设置和限流阶段只重审一次；持续新消息使结果失效时，使用当前上下文独立执行，
不无限重审。请求修订、设置或限流阶段改变后才重新判断。
明确请求已通过复审时先执行，只合入仍有效的短答；反复过时的旧闲聊让就绪的明确请求先行，
避免繁忙群聊一直重审、迟迟不答。
语义上的过时撤回需要高把握且快照仍有效；容量优先级的撤回规则见下文。明确求助/真实@保留。
重审失败保留请求并暂时回退到普通执行，不每100毫秒重复调用Jev。
默认0.85/0.90阈值是初始路由策略，尚不是线上准确率结论。

一批默认最多4条，同模型设置，共享一次人格、群档案、所选记忆及去重后的消息背景。
静默消息仍在共同上下文窗口内；图片、引用与语音保留来源，图片沿用原有像素绑定。
文本估算连同输出schema不得超过12,000（同时服从普通输入目标）；背景先按现有规则
裁剪，必需内容不截断。装不下时尝试较小批次或独立执行。图像及服务端附加token不在此估算内。

合批原生执行关闭动态工具、工作区执行、原生搜索、子Agent、自动目标续跑和可执行Skills。
当前原生版本仍可携带询问用户的工具定义；批次通过逐请求的needs_input返回问题，
不依赖该原生问答通路，不授予外部操作能力。
它只负责短答；Codex可逐条返回defer，将需要工具、贴图/图片发送、调研或长任务的请求
交回原有完整能力路径，不宣称这些能力不可用。defer状态持久化，避免同修订反复进入批次。
这不改变独立请求的表情数量或冷却设置。

输出按请求分别核验。某成员取消/修改只废弃该成员的旧结果，其他有效结果继续投递；
缺项、重复或无效结果不会被当作已完成，也不丢掉其他成员的有效结果。
共享模型线程不会绑定回各成员，后续独立续问不能恢复整批历史。
模型已经执行后失败（包括429）不会自动重放；一次批次失败只排一条故障提示，
但每个成员仍记录自己的失败。确认未提交的入口拒绝才恢复排队。

队列满时保留先前判定的独立请求意图；空位出现后建立请求，再按当前聊天进行积压重审。
明确求助优先接纳；若槽位被可选闲聊占满，撤回一条从未开始执行的可选接话并记录原因，
为明确请求腾出位置。已经执行、长任务、等待澄清、已有投递或被明确叫到的请求不参与此让位。
无关新消息仍在等待Jev判断时也能补入已判定的积压请求。
不会将旧消息重放进普通Jev当前消息时间线，也不会据此追加到后来创建的无关任务。
积压仍受现有消息存储容量约束，合批不是无限队列。原始消息记录不会因撤销接话而删除。
消息窗口清理可跳过活动来源，删除其后已处理且不再需要的记录，完整存档仍保留。
如果窗口全部被未完成工作占用，新消息会存档并标记为未入队，同时至多每分钟提示一次。
此时 /status、/cancel 等恢复命令继续按原权限处理；控制回执沿用独立的16条容量，
不会因一个对话的消息条数耗尽而关闭机器人。释放空间后，未入队消息需要重新发送。

当前支持一批内逐请求回应，尚不把一条QQ气泡绑定为多个请求共同的发送确认。
线上是否降低总输入、延迟及429频率，需要观察真实token和调用数；一次执行仍不能
等同于账号全部模型调用，限流的上游具体原因也未因这项改动得到确认。

`model_admission` 默认允许本机器人进程同时执行两个模型任务，相邻新启动至少间隔
一秒；同群前台串行和 mode-3 的既有节流继续生效。聊天、计划模型任务、记忆提取、
表情标注和原生图片使用同一个入口。Jev 判断、收消息、状态命令和固定文字提醒继续处理。
排队期间不占用模型执行超时，相关消息仍可合并和取消。

收到原生模型 429（包括其内部重试通知）后暂停新任务，按 30／60／120／240／300 秒
退避；这是应用保护策略，不是上游承诺的恢复时间。冷却后仅放行一个真实待处理任务
试探恢复；较早的并行请求成功不能清除较新的限流状态。只对确认没有 dispatch 的
入口拒绝重新排队，不能自动重放已执行工具的失败任务；
若原生初始化已经启用生命周期 Hook，较晚的入口拒绝也不会自动重跑该初始化。图片阶段等待自身入口，
不重跑已经完成的正文／工具阶段。取消时许可保留到所属原生进程清理结束。

额度耗尽与普通 429 分开记录；QQ／腾讯文档工具的 429 不触发模型入口。
入口状态只在当前进程内共享，不控制用户的其他 Codex 窗口、旧版 scheduler/exec 路径
或模型内部每次工具循环／原生子 agent 请求。它降低应用自己制造的并发和请求突发，
不能保证消除服务端拒绝。当前原生版本对部分通用 429 不提供原始原因和 Retry-After；
日志明确记录缺失，不将通用 429 认定为套餐额度耗尽或上下文过长。
