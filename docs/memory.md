# Soul、参与模式与记忆

Soul 统一描述机器人是谁、怎样表达和相处。默认是“有主见、略嘴欠的聪明群友”；管理员自定义的非空 Soul 优先。四种参与模式共享同一人格、回答质量和按任务展开的规则。模式只控制接话时机，不控制知识讲解的深度。旧配置中的 `reply_instructions` 保留为只读存档，不再按模式注入 Codex。

本轮没有启用无人回应时主动找话题或回复完成后自行续聊；这与一次回答拆成多个气泡是不同能力。

## 两层记忆与原始依据

- **正式记忆**：当前有效的归档记录，带来源、确定性、有效期和完整修订历史。归档不等于事实已经独立核实。
- **文档缓冲区**：Codex 自动提取、用户指定以及管理员编辑的变更草稿。未归档的草稿不作为正式记忆注入回答。
- **聊天原文**：仍由独立的历史库保存，可按消息引用检索。记忆是经过筛选的资料，不替代原始记录。

每条草稿包含编号与版本、创建/更新时间、来源类型、涉及成员、分类、正文、选择理由、确定性、原消息引用与时间、有效期、归档状态及更正目标。跨人物的第三方描述会保留推断标记，不冒充当事人确认。

## 回答时如何读取人物记忆

人物事实保留在当前会话的正式记忆库。Soul 只描述自然运用记忆的原则；不把群友档案复制进 Soul 或工作区 AGENTS.md。首次回复和同一请求的原生追加消息都会重新选取记忆快照。

选取对象包括请求作者、实际贡献者、结构化提及和引用原作者，以及当前消息/可用语音转写中明确提到的已知成员昵称。同名或身份索引达到容量上限时，不凭昵称选人；引用有身份冲突时也不猜测。资料读取不会把被提及者变成请求发起者或授予修改权限。

记忆主体使用 QQ 事件中的稳定用户 ID，在会话内投影成固定别名；昵称只用于阅读和辅助检索，改昵称不会创建新人物或改写正式记忆正文。上下文附带最新非空昵称与最多两个近期昵称观察，按原消息时间、序号排序；较晚收到的旧消息和空昵称不会覆盖新名称。同名成员仍以不同身份区分，不能凭名字合并或迁移记忆。`/memory records` 和 `/memory inbox` 显示关联成员的当前已知昵称及缩短的稳定别名；历史姓名未找到时显示别名，没有绑定特定成员的记录明确标为通用。显示用短别名不能替代工具所需的完整身份引用。

在这些人物范围内，用原文词语与宽泛话题重合排序，优先带入相关偏好、约束和短期状态。关系话题可带入涉及其中一人的有效关系记录，但不因此展开另一人的完整档案。当前实现是轻量检索，不保证理解所有隐含语义。快照最多包含 8 条正式记忆、2 条旧版确认资料，总计不超过 12 KiB；保留来源、确定性、有效期与版本，省略完整修订历史。过期、被替代和未归档的记录不作为当前事实自动注入。

Codex 可以继续用 `memory_manage list` 的 `subjects`（当前会话的 U/M 人物别名）、`category`、`contains` 和分页游标查询，再用 `read` 查看来源与完整修订。默认列表仅含有效正式记录；调查旧事实时显式设置 `include_inactive: true`。自动快照缺少某项不表示没有记忆，个性化建议应按需补查。查询保持群聊/私聊及不同会话隔离。

Soul 要求只在当前交流有用时自然使用共同记忆，区分自述、推断和玩笑，不将旧偏好当作固定标签。当前说法与旧资料冲突时应核对、更正。快照失败会显式说明不可用并继续处理请求，不影响机器人服务。

| 分类 | 示例 | 整理规则 |
| --- | --- | --- |
| 人物资料 `profile` | 自述职业、稳定的饮食偏好 | 避免从一次行为推断性格或身份 |
| 人物关系 `relationship` | 朋友、同事、明确陈述的恋爱关系 | 记录涉及双方和信息来源；玩笑不固化为事实 |
| 群通用偏好 `group_preference` | 回答要具体、群内约定的安静时段 | 一人的建议不写成全群共识 |
| 短期状态 `short_term` | 最近工作压力大、带实际日期的会议 | 使用绝对日期和有效期；到期后退出有效视图 |

“今晚没吃饭”“刚才在打游戏”等通常只需要聊天历史。它们可被标为 `context_only` 或 `discard`，不会自动归档。`uncertain` 草稿也会保留待核实，而不是因时间过去自动成为正式记录。记住会议不等于创建提醒任务。

## 每日整理

按照用户最新决定，默认**北京时间每天 04:00 整理，不发送提醒**。后台可调整整理时刻、每隔几天整理、是否自动从聊天提取、短期记忆默认有效天数。关闭自动提取仍会整理已有草稿；关闭记忆功能会暂停两者。

整理时按持久事件游标分页读取本会话已保存的聊天，包括 Jev 判为不回复的消息。每批最多 50 个事件，模型最多提出 8 条候选。原文和上下文有明确容量上限；未读的后续事件留待下一批处理。模型负责筛选、转述和分类，程序核对消息引用、作者、精确证据片段、字段范围及版本；这些校验不能证明模型的语义判断必然正确。

模型结果、归档和游标推进使用同一记忆事务。失败不推进游标，重试不跳过未处理内容。新的聊天请求会取消尚在生成的记忆整理，让正常回复优先。服务重启后按保存的日期和游标接续；错过时刻时可补做，不承诺精确到秒。

## 更正与版本

1. 默认更正先进入缓冲区，以追加条目关联被更正记录。旧正文和来源仍保存，但被替代的条目不再作为当前事实注入。
2. 直接改写既有正式记录须明确确认。Codex 可提出改写草稿；用户通过 `/memory apply 编号 版本` 或后台明确确认执行。后台“提出更正”本身不会立即改写。
3. 版本不匹配或目标在等待期间已变化时，停止该项更正并保留草稿，不覆盖新版。其他无冲突项目可以继续整理。
4. 短期记录到期后停止默认注入；历史仍可查阅。后继条目到期不会让已被替代的旧记录自动复活。

自然语言请求由 `clawmingle.memory_manage` 工具记录草稿。工具可分页查询正式记忆、草稿和旧版个人确认式资料，查看修订历史，以及编辑或撤回有权限的草稿。工具不能指定宿主机目录、其他会话或自行批准改写。所有者/涉及成员与管理员权限由程序根据真实消息身份核对。

常用命令：`/memory add 内容`、`/memory inbox`、`/memory records`、`/memory reject 编号 版本`、`/memory apply 编号 版本`。旧 `/memory list`、`confirm`、`replace` 继续处理旧版个人资料。

## 文件接入与后台

以下是相对于应用数据目录的路径；私聊使用独立的 `private/` 前缀，群聊与私聊不会因相同标识而混合。

```text
persona/IDENTITY.md                   共享名字、身份与角色（启用文件模式时）
persona/SOUL.md                       共享性格、价值取向与交流习惯
memory/groups/G<scope-digest>/
  store.json                         唯一事务真值，包括版本和处理游标
  authority.json                     旧版个人资料镜像
  authority/
    profiles.json                    当前有效人物资料
    relationships.json               当前有效人物关系
    group_preferences.json           当前有效通用偏好
    short_term.json                   当前有效短期状态
    revisions.json                   修订与历史视图
  documents/memory/
    CHANGES.json                      结构化草稿视图
    CHANGES.md                        可阅读的草稿文档视图
history/archive.sqlite               群聊原文和状态
private/history/archive.sqlite       私聊原文和状态
workspaces/<conversation-scope>/      Codex 任务文件和产物
```

文档和分类文件是从真值重建的视图。通过后台或记忆工具编辑草稿会同步更新这些视图；直接修改镜像文件不会反向导入。这样既有可阅读的群文档，也避免文件编辑绕过版本检查。这里的“群文档”指项目的文档记忆模块，未宣称已接入腾讯在线文档编辑。

后台展示目录用途、正式记忆、缓冲区、原文引用、修订和归档设置。它不提供任意宿主文件浏览。Codex 的 `/workspace` 用于任务文件，正式记忆通过受控工具访问，不把认证目录、数据库或其他项目挂进去。

现有手动备份同时包含群聊与私聊的 canonical 记忆文件，不备份可重建的文档镜像。自动历史备份是否开启仍由独立备份配置控制。本次不自动开启备份服务。

## 容量与回滚

首版沿用每个会话 1 MiB 的原子存储边界，分类记录和草稿各最多 256 条，每条最多 16 个版本。达到边界会拒绝新写入并报告错误，保留既有数据，不自动清空历史。长期使用后需要分片或冷归档时，必须另做迁移，不能通过删除真值腾空间。

新存储可读取旧数据；写入新分类记忆后，旧程序不能直接读取新字段。部署前备份 canonical 文件，回滚时保留新增数据副本并检查兼容性，禁止盲目覆盖正在使用的记忆库。
